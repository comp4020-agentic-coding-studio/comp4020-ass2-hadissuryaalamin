# Task 002 — week 7 content (lane A)

## Alt text for week 7's three `![bg …]` directives — architecturally impossible, not a gap

Read `astromotion`'s rendering pipeline directly (`remark-deck-bg.ts`,
`parse-helpers.ts`): `parseBgModifiers` recognises only `left`/`right`,
`contain`/`cover`, and the three CSS-filter tokens (`blur:`/`brightness:`/
`saturate:`). Any other token, including a would-be `alt:` token, is silently
dropped — never stored, never reaches the rendered output, which is always a
plain `<div style="background-image:...">`, never a real `<img>`. It is
architecturally impossible to give a `![bg …]` directive real alt text in
this astromotion version.

This is not a gap against the spec: axe's image-alt rule only fires on real
`<img>`/`role=img` elements missing a name, and the epic's own accessibility
rules already say `![bg …]` backgrounds are decorative-only in this epic's
scope. All three of week 7's bg images (chefs-knife.jpg, knife-set.jpg,
sharpening-stone.jpg) are confirmed decorative-only — no slide content
depends on them. No `alt:` token added (it would be a no-op, misrepresenting
the change).

1280×800 (clear of the 800px viewport), 375×812 unaffected (517.98px
