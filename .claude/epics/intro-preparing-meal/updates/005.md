## Related-edge decisions (read before touching either file)

- The task file suggested the lecture also carry a forward `related:` to
  `sessions/08-*` (task 002's file, weeks 7-12 sessions). Task 002 hasn't
  run yet and its slug for week 8 is not fixed by the epic (unlike the
  `lectures/week-0N` pattern, session slugs are free-form, e.g.
  `01-getting-started`, `02-first-review`), so I did not add that ref here —
  it would be a guess and risks a dangling content ref at build time. Task
  002's own task file already commits to declaring
  `related:` on the *session* side pointing at `lectures/week-08` and at the
  week 1 session, which is enough: this codebase's existing pattern
  (`lectures/week-01` → `sessions/01-getting-started`, not declared back)
  shows one-sided `related:` is treated as a bidirectional graph edge by
  `astro-course-university`'s node graph, so the session-side declaration
  alone will connect week 8's lecture and session once task 002 lands.
  No follow-up action needed on this file for that edge.
- The person entry's `related: [lectures/week-08]` is safe because both
  files were created together in this task — no dangling ref.
- Per task 007's schema note (`updates/007.md`): the `people` collection
  schema in `src/content.config.ts` doesn't declare a `related` field and
  isn't `.loose()`, so Zod strips it from the typed `getCollection("people")`
  data — but `astro-course-university` reads `related:` from raw frontmatter
  independent of the schema, and `people` is in `graphCollections`
  (`site-config.ts`), so this edge still reaches `dist/api/index.json`.
