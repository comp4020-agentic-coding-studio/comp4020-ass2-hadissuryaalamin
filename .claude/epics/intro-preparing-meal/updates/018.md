# Task 018 — Deck images (all 12 decks)

Status: completed.

## What was done

Added image references to all 12 decks (`src/decks/week-01.deck.mdx` through
`week-12.deck.mdx`) without altering any existing slide text. Every deck got
a full-bleed, dimmed title-slide background (`![bg blur:2px
brightness:0.5](...)`) plus one to three additional images placed at
topically-relevant slides — anatomy bullet lists, nutrition tables,
technique sections — using `![bg right:NN% contain](...)` or plain inline
`![alt](...)` markdown, per astromotion's documented syntax.

Images were sourced from Wikimedia Commons (search + imageinfo API,
resized via Commons' own thumbnailing service) and downloaded into
`src/decks/assets/<week-slug>/`. Each week folder also has a `SOURCES.md`
recording, per file: the Commons file title, source URL, licence and
artist.

A handful of weeks ship with 2 images rather than 3 (week-01, week-06)
because repeated Commons searches (mise en place, chopped onion, marble
cutting board, raw chicken breast) kept returning off-topic matches
(a logo, an art sculpture, a plant-based mock-meat product, a scanned
book cover) with no acceptable real photograph found after several
retries — judged better to ship fewer, correct images than pad with a
wrong one. Every image that did ship was visually inspected (via the
Read tool) before being trusted, since Commons' search ranking has no
reliable signal for "this is actually a photo of X."

File scope respected: only the 12 `week-NN.deck.mdx` files and new files
under `src/decks/assets/` were touched. `src/content/*` and components
were left alone.

**Platform-specific finding, not a defect in the deliverable.** On this
Windows dev machine, `astromotion`'s `remark-deck-bg.ts` (`resolveAssetUrl`,
a third-party package pinned at `astromotion@v0.23.0`, installed under
`node_modules` and gitignored) builds the on-disk path with `node:path`'s
`resolve()`, which returns backslash-separated paths on Windows, then
looks for the substring `"/src/"` to rewrite the URL with the site's base
prefix. That match fails on Windows (backslashes, not forward slashes),
so on this machine background-image URLs are emitted unresolved
(`./assets/week-NN/...`, relative to the page's own directory) and 404
locally in `pnpm dev`/a local `pnpm build` preview. Root-caused this by
tracing `remark-deck-bg.ts`, then confirmed the fix (normalizing
backslashes before the `indexOf` check) makes every one of the 12 decks'
background images resolve to the correct `/`, `<base>`, `src/decks/
assets/...` URL and land on a real file in `dist/` — applied that fix
*temporarily, locally only* to confirm the hypothesis, then reverted it
byte-for-byte (diffed clean against a backup) since it lives in a
gitignored, not-shipped dependency and isn't part of this task's file
scope. This repo's CI (`.github/workflows/checks.yml`) runs on
`ubuntu-latest`, where `node:path`'s `resolve()` already produces
forward-slash paths, so the `"/src/"` match succeeds unpatched and this
does not affect the actual build/deploy target — consistent with the
other Windows-only quirk already on record in this repo's `CLAUDE.md`
("the theme's automatic layout does not fire on Windows"). Recommend the
epic owner flag this upstream (astromotion's `remark-deck-bg.ts` should
normalize path separators before the `"/src/"` check) so Windows-based
`pnpm dev` previews of decks with background images work correctly too.
