## Diagnosis (reasoned from source, not re-verified by screenshot)

Same bug class as decks 1 and 5–10, already diagnosed and confirmed by
screenshot in this series' earlier epics (see
`weeks34-deck-improvement/updates/001.md`): astromotion's `![bg ...]`
directive resolves its generated CSS `background-image: url(...)` against
the *served page path* (e.g. `/decks/week-11/`), not the deck source
file's own location. A path written `./assets/week-11/<file>` (relative to
`src/decks/week-11.deck.mdx`) 404s once served, because the browser
resolves it as `/decks/week-11/assets/week-11/<file>`, which does not
exist — the asset actually lands under
`dist/src/decks/assets/week-11/<file>` (build-relative to the repo root,
per astromotion's copy behaviour, previously confirmed empirically by
weeks34 task 001's direct inspection of `dist/`).

I could not re-run the before/after screenshot confirmation myself in this
job (see above), but the bug is not in question — it is the same
mechanism, same directive syntax, same asset-copy behaviour as every
occurrence this series has already found and fixed identically. Read the
four `![bg ...]` lines directly from the original files to confirm the
broken form was present before editing:

- `src/decks/week-11.deck.mdx:8` — `![bg blur:2px brightness:0.5](./assets/week-11/frying-pan-cooking.jpg)`
- `src/decks/week-11.deck.mdx:87` — `![bg right:30% contain](./assets/week-11/thermometer-cooking.jpg)`
- `src/decks/week-12.deck.mdx:8` — `![bg blur:2px brightness:0.5](./assets/week-12/cooking-competition.jpg)`
- `src/decks/week-12.deck.mdx:62` — `![bg right:32% contain](./assets/week-12/plated-presentation.jpg)`
