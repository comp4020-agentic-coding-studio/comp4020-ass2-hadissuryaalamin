# 001 — Fix week-02 deck background images

## Environment

- Worktree: `week2-deck-improve` (branch `worktree-week2-deck-improve`).
- Repo base path resolved from `git remote get-url origin`
  (`comp4020-ass2-hadissuryaalamin`, not an `<owner>.github.io` repo) →
  `/comp4020-ass2-hadissuryaalamin/`, per `scripts/pages-base.ts`.
- Before starting a dev server, checked for stale processes: `netstat` showed
  listeners on ports 4321–4323, and `pnpm exec astro dev status` (run from
  this worktree) reported "No dev server is running" — i.e. those were other
  worktrees' servers, not this one. Confirmed via
  `Get-CimInstance Win32_Process` on each PID's command line: 4321 was
  `epic-intro-preparing-meal`, 4322 was the bare main repo checkout, 4323 was
  `week1-deck-improve`. None served this worktree, so they were left running
  and `pnpm dev` here bound its own port (4324) instead of reusing/killing a
  stale one.

## Observation before the fix

Verified by screenshot and network inspection with headless Chromium
(Playwright), not asserted from the epic's say-so.

- Fetched `http://localhost:4324/comp4020-ass2-hadissuryaalamin/decks/week-02/`
  and inspected the rendered HTML: the title slide's background div carried
  `style="background-image: url('./assets/week-02/vegetable-market.jpg'); ..."`
  and the "Three checks" slide's background div carried
  `url('./assets/week-02/carrots.jpg')` — i.e. exactly the literal
  `![bg ...]` paths from the MDX source, unrewritten.
- Requesting that literal path
  (`/comp4020-ass2-hadissuryaalamin/decks/week-02/assets/week-02/vegetable-market.jpg`,
  and the carrots equivalent) both returned **404** via `curl`.
- Requesting the path the fix would use instead
  (`/comp4020-ass2-hadissuryaalamin/src/decks/assets/week-02/vegetable-market.jpg`
  and `.../carrots.jpg`) both returned **200** — the files exist there, in
  dev, already (astro/astromotion serves `src/decks/assets/<deck>/` at that
  URL; it's the page's own relative-path math that's wrong, not the asset
  location).
- Screenshotted both slides with Playwright (`page.on("pageerror"/"console")`
  wired up): both requests logged
  `console:error:Failed to load resource: the server responded with a status
  of 404 (Not Found)`, and the screenshots
  (`before-dev-title.png`, `before-dev-carrots.png`) show a flat theme-colour
  background on the title slide (no market photo, no blur/darken) and a
  plain dark background on the "Three checks" slide (no carrots photo in the
  right 30% panel).
- **Diagnosis confirmed: this is the astromotion relative-path bug**
  (`week1-deck-improvement` §6), not the Windows path-separator quirk floated
  elsewhere (`updates/018.md` of the parent epic). The failing URL uses
  forward slashes throughout and 404s identically regardless of OS — the
  literal `./assets/week-02/<file>` resolves, correctly per URL rules,
  against the page URL `/decks/week-02/`, landing one directory short of
  where astromotion actually copies/serves the file. There is no
  separator-mangling involved; this reproduces on this Windows machine for
  the reason the epic already suspected.

## Fix applied

`src/decks/week-02.deck.mdx` — rewrote both `![bg ...]` image paths from
page-relative (`./assets/week-02/...`, wrong depth) to build-relative
(`../../src/decks/assets/week-02/...`), matching the depth verified by
directly requesting that URL and getting 200:

- line 8: `![bg blur:2px brightness:0.5](./assets/week-02/vegetable-market.jpg)`
  → `![bg blur:2px brightness:0.5](../../src/decks/assets/week-02/vegetable-market.jpg)`
- line 143: `![bg right:30% contain](./assets/week-02/carrots.jpg)`
  → `![bg right:30% contain](../../src/decks/assets/week-02/carrots.jpg)`

Same two-levels-up depth as week 1's fix, confirmed independently for week 2
(both decks' `/decks/<slug>/` route sits at the same depth from site root).

No other lines touched. `astro.config.ts`, `week-03..12.deck.mdx` and the
pinned `astromotion` version were not touched.
