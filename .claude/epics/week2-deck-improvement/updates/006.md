## 2. Screenshot verification — real defect found and fixed

Walked the entire deck (28 top-level sections) with a Playwright script
(`updates/verify_week02.py`), screenshotting every slide at desktop
(1280×800) and mobile (375×812), reading each slide's DOM (`scrollHeight` vs
`clientHeight`, every `<img>`'s `src`/`alt`/`naturalWidth`/`complete`,
background-image computed style).

**Defect found:** 7 slides had their inline photograph clipped at the bottom
of Reveal's fixed 1280×720 canvas — `.reveal`/`body` both have
`overflow: hidden` with no scroll mechanism, so this is real, permanent
clipping a viewer would see, not a false alarm. Affected: Julienne,
Batonnet, Brunoise, Small dice, Chiffonade (task 002's cut-shape photos,
each 540–1147 px natural height with no size cap), and Not refrigerated,
Refrigerated (task 003's storage photos). This is invisible to
`pnpm check`: `astromotion`'s build-time check is a static-DOM structural
check with no pixel layout, and the one tool in this dependency tree that
does measure real pixel overflow (`astromotion-check`, Puppeteer-based)
explicitly excludes images/backgrounds from its overflow rule by design and
isn't even installed here (no `puppeteer-core` dependency). This is exactly
the gap this repo's `CLAUDE.md` names: "A jsdom-based check cannot see
layout, overflow or a 404'd background."

**Fix applied** (`src/decks/week-02.deck.mdx`, the 7 slides above): converted
each image from markdown `![alt](./assets/week-02/<file>)` to a raw HTML
`<img src="../../src/decks/assets/week-02/<file>" alt="..."
style="max-height: <N>px; width: auto; margin: 15px auto; display: block;" />`
— same corrected relative-path pattern task 001 established for background
images (raw `<img>` tags bypass Astro's markdown-image path resolution,
confirmed by testing before applying it everywhere). Alt text is unchanged,
word for word, from the original markdown. `max-height` values (260px for
the five cut-shape slides, 220px for Not refrigerated, 180px for
Refrigerated) were chosen from each slide's measured content-height budget
against the 720px canvas; `theme.css`'s existing
`.compare figure img { max-height: 19rem }` (task 004) was used only as a
stylistic reference — that shared file was not touched.

Re-ran the full-deck script after the fix, at both viewports. Result: all 7
in-scope overflows resolved. One overflow remains — slide 3, "Families,
briefly" (the `onions.jpg` slide) — confirmed via
`git show 727de41^:src/decks/week-02.deck.mdx` to **predate this epic
entirely** (same image and layout before task 001's first commit; only its
caption text was later touched by task 005). This is a real, pre-existing
defect but outside this epic's scope and not something I fixed, per the
verification task's instruction not to redo prior content decisions or
reach beyond the epic's remit. Flagging it here for visibility.

Also confirmed at both viewports across the whole deck: both `![bg ...]`
backgrounds (title slide, market-comparison slide's predecessor) paint, no
element overlap, every image has non-empty `alt`, every image's
`naturalWidth > 0` / `complete === true` (no 404s or broken loads), no
`pageerror`/console errors during a full slide-by-slide walk.

Additionally verified in a fresh production `dist` build (not just
`astro dev`): all 7 fixed `<img src="../../src/decks/assets/week-02/...">`
paths resolve — `dist/decks/week-02/index.html` carries the same relative
paths, and `dist/src/decks/assets/week-02/` contains every one of the 7

Evidence kept in `updates/`: `verify_week02.py` (the script),
