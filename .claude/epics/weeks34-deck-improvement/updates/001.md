## Before-fix screenshot verification (bug confirmed, per epic instruction not to skip)

Script: `.claude/epics/weeks34-deck-improvement/updates/screenshot_bg.py`
(adapted from week 2's `screenshot_week02.py`/`verify_week02.py` pattern —
reports the slide's resolved `.slide-bg` `background-image` URL plus any
`pageerror`/console errors, and screenshots the slide).

All four directives confirmed broken, each with a matching 404 console error
for the resolved asset URL:

| File | Slide | Console evidence | Screenshot |
|---|---|---|---|
| week-03 title | `fish-market.jpg` | resolved `background-image` request: `http://localhost:4325/comp4020-ass2-hadissuryaalamin/decks/week-03/assets/week-03/fish-market.jpg` — 404 | `screenshots/before-week03-title.png` — solid orange background, no photo |
| week-03 slide 3 ("leg and thigh versus breast") | `chicken-thigh.jpg` | 2 console 404s on this navigation (title's still-mounted background element plus this slide's own `chicken-thigh.jpg` request); the script's reported `.slide-bg` fell back to the first such element in the DOM (title's), so the URL text isn't this slide's own — the screenshot is the reliable evidence here | `screenshots/before-week03-chickenthigh.png` — right-side `contain` panel is entirely blank |
| week-04 title | `raw-steak.jpg` | resolved request: `http://localhost:4325/comp4020-ass2-hadissuryaalamin/decks/week-04/assets/week-04/raw-steak.jpg` — 404 | `screenshots/before-week04-title.png` |
| week-04 slide 14 ("Fat, protein and calories per 100 g") | `ground-beef.jpg` | same pattern as the week-03 mid-deck case: 2 console 404s, script's reported URL not reliable for this slide, screenshot is | `screenshots/before-week04-groundbeef.png` — right-side panel blank |

**This settles the diagnosis stated in the epic**: the browser resolves the
`![bg …]` CSS `url()` against the *served page path*
(`/decks/week-03/`, `/decks/week-04/`), not the deck source file's location —
confirmed directly from the resolved request URL in each case, not inferred.
This is a URL-resolution bug, not a Windows path-separator artifact (all
paths use forward slashes throughout; the fix behaves identically
cross-platform).

## Fix

Rewrote all four directives from `./assets/week-0N/<file>` (deck-source-relative)
to `../../src/decks/assets/week-0N/<file>` (build-relative), per the epic's rule.
Did not touch any plain markdown inline image (none exist yet in these two
decks at this stage) or any other deck.

- `src/decks/week-03.deck.mdx` line 8: `fish-market.jpg`
- `src/decks/week-03.deck.mdx` line 47: `chicken-thigh.jpg`
- `src/decks/week-04.deck.mdx` line 8: `raw-steak.jpg`
- `src/decks/week-04.deck.mdx` line 145: `ground-beef.jpg`

## After-fix verification

Re-ran the same screenshot script (same dev server, same slide indices) after
the edit: all four `.slide-bg` `background-image` values now resolve to
`200`, and the screenshots show the actual photographs painting. No
`pageerror`/console errors on any of the four requests post-fix.

Then verified in a **production build**: `pnpm build` followed by
`pnpm preview`, re-running the same script against the preview server for all
four directives — all four painted, all four 200, matching the dev-mode
result identically (the described bug only manifests once the built asset
lives under `dist/src/decks/assets/...` — dev mode alone can mask this, so
both were required).
